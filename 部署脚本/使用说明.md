# Yu_project：服务器部署脚本

本目录只是一套待运行工具。编写脚本不代表已连接服务器或部署成功。

## 部署方案

- 服务器：`64.90.13.128`，SSH 用户 `root`，默认 SSH 端口 `22`。
- 浏览器入口：`http://64.90.13.128:9091/`，不需要域名。
- 端口映射：服务器 `9091` → 容器 `8000`，不会改动本机项目的 `8000`。
- 独立 Docker Compose 项目：`valuation9091`。
- 独立服务器目录：`/opt/valuation-web-9091`。
- 只部署当前仓库根目录的代码、依赖和原件模板；不上传本机任务库、用户 PDF、缓存、日志及部署脚本自身。
- 服务通过 Docker `unless-stopped` 自动重启；手动停止后，要运行“启动”恢复。

## 先决条件与安全

1. 本机 Python 3.9 或以上，执行脚本前安装 `requirements.txt`。
2. 服务器需要 Linux、Python 3.9 或以上、Docker Engine、Compose v2 插件，并能访问镜像仓库及 Python 包源。
3. 脚本**不自动安装 Docker、不升级系统、不修改防火墙、不清理其他项目**。缺少组件时会明确退出，后续确认服务器环境后再处理。
4. 应用没有账号系统，HTTP 不加密。供一两人使用时，应在云安全组/服务器网络防火墙中仅允许办公电脑的公网 IP 访问 TCP `9091`，SSH `22` 同样限制来源。不要将 `9091` 对所有人开放。注意 Docker 发布端口可能绕过某些主机防火墙规则，优先使用云端网络访问控制并验证实际效果。
5. 密码运行时由 `getpass` 输入，不显示、不写入配置、不写入日志。脚本没有保存对话里提供的密码。此前已在对话中发送过 root 密码，建议正式使用前更换，并优先改用 SSH 密钥。
6. 首次连接会显示 SSH 主机指纹，需要通过服务器控制台核对后输入“信任”。以后主机指纹变化会拒绝连接，不自动接受新指纹。
7. 执行部署/备份/停止前确认没有正在生成的任务；更新会短暂停服，在途任务会按应用的中断恢复逻辑处理。

## 本机执行方式

在 PowerShell 中进入本目录：

```powershell
cd "E:\ZHYWork\Yu_project\数据报告与模板文档数据兼容研究\部署脚本"
python -m pip install -r requirements.txt
```

**默认只预览，不连接服务器：**

```powershell

```

以后确认要执行时，才加 `--执行`：

```powershell
python 部署管理.py 检查 --执行
python 部署管理.py 部署 --执行
python 部署管理.py 状态 --执行
python 部署管理.py 日志 --执行
python 部署管理.py 停止 --执行
python 部署管理.py 启动 --执行

```

每次实际操作还会要求输入对应操作名称，防止误触。密码交互输入即可，不需要修改源代码。
使用 SSH 私钥时，增加 `--密钥 "C:\路径\id_ed25519"`。
需要调整服务器、SSH 端口、项目目录或监听地址时，编辑 `部署配置.json`，不要把密码加进去。本目录已将项目目录配置为上一级的仓库根目录。

## 部署实际会做什么

1. 本机打包当前仓库代码，排除任务数据和秘密文件；上传到独立临时目录。
2. 校验上传文件 SHA-256，检查 Docker、Compose、端口和目标目录归属。
3. 解压到独立 `releases/<版本号>`，生成仅用于远端的 `compose.json`。
4. 先构建新镜像，构建成功之前不停止已有服务。
5. 更新部署时仅停止本项目，备份服务器 `data/`，再启动新版本。
6. 检查 `/healthz`；失败会展示本项目日志并保留数据，不假报部署成功，不自动回退数据库。
7. 保留旧版本、镜像和备份，不执行 `docker system prune`、`down -v` 或删除旧项目的操作。

## 已有程序和数据是否会被覆盖

- 当服务器目录仍是 `/opt/valuation-web-9091`、Docker 项目名仍是 `valuation9091`、端口仍是 `9091` 时，这次操作属于**更新同一个程序**：会停止并替换这个项目的容器，重新构建镜像，但继续挂载同一个服务器 `data/` 目录。
- 部署脚本不会删除或清空服务器 `data/`，不会执行 `docker compose down -v`，也不会删除旧版本、旧镜像和备份。任务数据库、上传 PDF、历史模型和日志会保留；应用启动时可能按代码版本自动补充 SQLite 字段，这是数据库结构升级，不是清空数据。
- 更新前会把服务器 `data/` 打包到同目录的 `backups/`。备份失败时不会继续切换版本；目标目录没有部署标记、属于其他项目、端口被其他容器占用时，脚本会拒绝操作。
- 当前部署配置不是并行部署。若要保留旧程序同时运行，必须改用新的服务器目录、Docker 项目名和端口，并先确认新目录不含其他内容；否则脚本会按同一程序更新处理。
- 新镜像构建完成后才停止旧容器，但健康检查失败时脚本不会自动回滚旧版本。此时数据仍保留、旧版本和备份仍在，但需要人工执行“状态/日志”后决定回退；不要直接删除 `data/`。

运行超时或网络中断不意味着远端操作已结束。不要连续重复部署，先重新连接查看状态。
操作锁会防止同时执行多个修改操作。只有安装依赖与加 `--执行` 的命令会实际产生相应影响。

## 数据与排错位置

| 位置 | 用途 |
| --- | --- |
| 服务器 `data/` | 持久化任务数据库、上传财报、模型、应用日志 |
| 服务器 `releases/` | 每次发布的代码和 Compose 配置 |
| 服务器 `backups/` | 停服后打包的数据备份，不会自动下载到本机 |
| 服务器 `current.txt` | 当前尝试运行的版本 |
| 服务器 `previous.txt` | 上一次版本编号，供人工排查或回退参考 |
| 服务器 `last-success.txt` | 最近一次健康检查通过的部署版本 |
| 本机 `部署记录/` | 远程执行输出，不含 SSH 密码 |

服务器备份仍在同一台服务器上，不能代替异地备份。建议另行定期下载备份。
不要未经核对就回退旧数据库或删 `data/`。脚本不提供自动删除数据或自动回滚命令。
